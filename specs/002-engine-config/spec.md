# 功能规范: 引擎配置规范化与自定义引擎支持

**功能分支**: `feature/engine-config`
**创建时间**: 2026-02-12
**状态**: 草稿
**输入**: 用户描述: "规范化引擎的配置以及支持自定义引擎，同时删除现有的 cyclone 引擎"

## 用户场景与测试

### 用户故事 1 - 删除 Cyclone 引擎 (优先级: P1)

用户启动飞将象棋后, 菜单中不再显示"象棋旋风"引擎选项.
应用内所有对 Cyclone 引擎的引用被彻底移除, 相关资源文件一并清理.

**优先级原因**: 这是清理性任务, 是后续引擎配置重构的前提,
消除无用代码降低维护负担.

**独立测试**: 启动应用 → 游戏设置 → 红方/黑方子菜单中不出现
"象棋旋风" → 选择其他引擎正常对局.

**验收场景**:

1. **给定** 应用已启动, **当** 打开"游戏设置 → 红方"菜单时,
   **那么** 不显示"象棋旋风"选项, 仅显示象眼、佳佳、南奥及已加载的自定义引擎.
2. **给定** 项目源码, **当** 搜索 `CYCLONE` 或 `cyclone` 时,
   **那么** 不存在任何引用(常量定义、引擎创建、菜单项).
3. **给定** 构建产物, **当** 检查 `assets/engine/` 目录时,
   **那么** 不存在 `cyclone/` 子目录.

---

### 用户故事 2 - 引擎配置数据持久化 (优先级: P1)

应用使用 JSON 配置文件管理所有引擎信息(内置引擎和自定义引擎),
配置文件存储在用户数据目录(`%APPDATA%/飞将象棋/engines.json`).
首次启动时自动生成包含内置引擎(象眼、佳佳、南奥)的默认配置.

**优先级原因**: 统一的配置模型是自定义引擎功能的基础,
也为未来引擎参数设置提供数据结构支撑.

**独立测试**: 删除 `engines.json` → 启动应用 → 验证自动生成
默认配置文件 → 关闭应用 → 再次启动 → 配置正确加载.

**验收场景**:

1. **给定** 用户数据目录中不存在 `engines.json`,
   **当** 应用首次启动时,
   **那么** 自动创建 `engines.json`, 包含 3 个内置引擎的配置信息
   (名称、路径、协议类型、是否内置、默认参数).
2. **给定** `engines.json` 已存在且包含合法配置,
   **当** 应用启动时,
   **那么** 从配置文件加载引擎列表, 菜单中正确显示所有引擎.
3. **给定** `engines.json` 内容损坏(JSON 解析失败),
   **当** 应用启动时,
   **那么** 备份损坏文件为 `engines.json.bak`,
   重新生成默认配置, 并在控制台输出警告日志.

---

### 用户故事 3 - 加载自定义引擎 (优先级: P1) 🎯 MVP

用户通过菜单"引擎设置 → 加载引擎"选择一个 UCCI/UCI 引擎的 EXE
文件, 应用自动检测引擎协议类型(UCCI 或 UCI), 获取引擎名称,
将其添加到引擎列表中. 之后用户可在"游戏设置"的红方/黑方子菜单
中选择该自定义引擎进行对局.

**优先级原因**: 这是本次迭代的核心功能, 满足用户加载第三方引擎
的需求, 显著扩展应用的引擎生态.

**独立测试**: 从互联网下载一个 UCCI/UCI 引擎 → 解压到本地目录 →
通过菜单加载 → 选择该引擎作为黑方 → 与 AI 正常对局.

**验收场景**:

1. **给定** 用户点击"引擎设置 → 加载引擎",
   **当** 在文件选择对话框中选择一个合法的 UCCI/UCI 引擎 EXE 文件时,
   **那么** 应用启动引擎进程, 发送 `ucci` 命令尝试握手,
   若收到 `ucciok` 则识别为 UCCI 引擎;
   否则发送 `uci` 命令, 若收到 `uciok` 则识别为 UCI 引擎;
   从返回的 `id name` 行提取引擎显示名称;
   成功后将引擎信息写入 `engines.json`, 并在菜单中立即可用.
2. **给定** 用户选择了一个非引擎的 EXE 文件(无法完成协议握手),
   **当** 握手超时(5 秒)或进程异常退出时,
   **那么** 显示通知"无法识别引擎协议, 请确认文件为合法的 UCCI/UCI 引擎",
   不修改配置文件.
3. **给定** 用户加载了一个新引擎,
   **当** 关闭并重新启动应用时,
   **那么** 该引擎仍然出现在菜单中, 可正常使用.
4. **给定** 用户重复加载同一路径的引擎文件,
   **当** 检测到路径重复时,
   **那么** 显示通知"该引擎已存在", 不重复添加.

### 用户故事 4 - 移除自定义引擎 (优先级: P2)

用户通过菜单"引擎设置 → 管理引擎"可以查看已加载的自定义引擎列表,
并移除不再需要的引擎. 内置引擎不可移除.

**优先级原因**: 引擎管理的完整闭环, 允许用户清理不再使用的引擎.

**独立测试**: 加载一个自定义引擎 → 通过管理引擎菜单移除 →
验证菜单中不再显示该引擎 → 重启应用后仍不显示.

**验收场景**:

1. **给定** 用户已加载 2 个自定义引擎,
   **当** 点击"引擎设置 → 管理引擎"时,
   **那么** 显示子菜单, 列出所有自定义引擎(每个引擎名称后带"❌ 移除"操作).
   内置引擎不出现在此列表中.
2. **给定** 用户点击某自定义引擎的"❌ 移除"操作,
   **当** 该引擎当前未被任何对局方使用时,
   **那么** 从 `engines.json` 中删除该引擎记录, 菜单立即更新.
3. **给定** 用户点击某自定义引擎的"❌ 移除"操作,
   **当** 该引擎当前正被红方或黑方使用时,
   **那么** 显示通知"该引擎正在使用中, 请先切换到其他引擎",
   不执行移除操作.

---

### 用户故事 5 - 引擎路径失效处理 (优先级: P3)

当自定义引擎的 EXE 文件被移动或删除后, 应用能优雅地处理这种情况,
不会崩溃, 并提示用户引擎不可用.

**优先级原因**: 健壮性保障, 防止因外部文件变更导致应用异常.

**独立测试**: 加载一个自定义引擎 → 手动删除其 EXE 文件 →
重启应用 → 验证菜单中该引擎标记为不可用.

**验收场景**:

1. **给定** 配置文件中包含一个自定义引擎, 但其 EXE 路径不存在,
   **当** 应用启动加载引擎列表时,
   **那么** 该引擎在菜单中显示为灰色(禁用状态), 附加"(不可用)"标记.
2. **给定** 用户尝试选择一个路径失效的引擎作为对局方,
   **当** 点击该菜单项时,
   **那么** 显示通知"引擎文件不存在, 请重新加载或移除该引擎".

### 用户故事 6 - 引擎集成代码优化 (优先级: P1)

优化引擎通信层 (`UCCI.ts`) 的代码质量和架构, 修复现有 `info` 解析 bug,
为未来的局面分析功能 (实时评估分数、多路 PV 线) 做好技术准备.
本故事不实现分析 UI, 仅确保引擎通信层具备流式 info 事件推送
和 `go infinite` 分析模式的能力.

**优先级原因**: 现有 `infoAndMove()` 中 `info` 行解析存在多处 bug
(depth/nps 赋值到 score 字段, infoObj 未推入 pvList, pv 按固定步长 2 解析不正确),
这些 bug 影响当前对局的走棋质量评估数据正确性.
同时, 缺乏事件驱动的 info 流式推送和 `go infinite` 支持,
无法在后续版本中实现局面分析功能.

**独立测试**: 发送 `go movetime 3000` 给 UCI 引擎 →
验证返回的 `InfoAndMove.pvList` 包含正确的 depth/score/pv 数据 →
使用 `onInfo` 回调验证每轮 depth 都能触发回调事件.

**验收场景**:

1. **给定** 引擎返回多行 `info depth N score cp X ... pv e2e4 d7d5 ...`,
   **当** `infoAndMove()` 解析完成时,
   **那么** `pvList` 包含每个 depth 对应的 `Info` 对象,
   其中 `depth` 字段为实际深度值, `score` 字段为 centipawn 评分,
   `pv` 数组包含完整的变例走法序列.
2. **给定** 引擎返回 `info ... score mate 5`,
   **当** 解析 info 行时,
   **那么** `Info.scoreType` 为 `'mate'`, `Info.score` 为 `5`.
3. **给定** 调用 `infoAndMove()` 时传入 `onInfo` 回调,
   **当** 引擎输出每行 `info` 时,
   **那么** `onInfo` 被实时调用, 参数为解析后的 `Info` 对象,
   不必等待 `bestmove` 结束.
4. **给定** 调用 `analyzePosition(fen)` 启动无限分析,
   **当** 引擎进入 `go infinite` 模式时,
   **那么** 持续通过 `onInfo` 回调推送分析数据,
   直到调用 `stopAnalysis()` 发送 `stop` 命令.

---

### 边界情况

- 引擎 EXE 文件路径包含中文或空格时, 进程能否正常启动?
  → MUST 正确处理, 使用 `spawn` 时不对路径做额外转义.
- 引擎进程启动后长时间无响应(挂起)如何处理?
  → 设置 5 秒握手超时, 超时后终止进程并报错.
- 多个引擎同时运行(红方和黑方均为不同引擎)时的资源管理?
  → 沿用现有 `feijiang.ts` 中的 `engines` Map 缓存机制,
  键从硬编码常量变为配置文件中的引擎 ID.
- `engines.json` 文件被外部程序修改(格式不完整)时如何处理?
  → 加载时校验必填字段, 跳过无效条目并在日志中记录警告.

## 需求

### 功能需求

- **FR-001**: 系统 MUST 从代码和资源中彻底移除 Cyclone 引擎的所有引用
  (常量定义、引擎创建逻辑、菜单项、`assets/engine/cyclone/` 目录).
- **FR-002**: 系统 MUST 使用 JSON 配置文件 (`engines.json`) 管理引擎列表,
  文件位于 `%APPDATA%/飞将象棋/` 目录.
- **FR-003**: 配置文件 MUST 在首次启动时自动生成,
  包含内置引擎(象眼、佳佳、南奥)的默认配置.
- **FR-004**: 系统 MUST 提供"加载引擎"菜单项,
  允许用户通过文件选择对话框指定引擎 EXE 文件.
- **FR-005**: 系统 MUST 自动检测引擎协议类型(UCCI 或 UCI),
  通过依次尝试 `ucci` 和 `uci` 握手命令实现.
- **FR-006**: 系统 MUST 从引擎握手响应中提取 `id name` 作为显示名称.
- **FR-007**: 加载成功的自定义引擎 MUST 立即出现在
  "游戏设置 → 红方/黑方"子菜单中, 无需重启应用.
- **FR-008**: 系统 MUST 提供移除自定义引擎的功能,
  内置引擎不可被移除.
- **FR-009**: 系统 MUST 在启动时校验自定义引擎 EXE 文件是否存在,
  不存在的引擎标记为不可用.
- **FR-010**: 配置文件损坏时, 系统 MUST 备份原文件并重新生成默认配置.
- **FR-011**: `infoAndMove()` MUST 正确解析 UCI/UCCI `info` 行中的
  `depth`、`seldepth`、`score cp`、`score mate`、`nodes`、`nps`、`time`、
  `multipv`、`pv` 字段, 每个字段映射到对应的类型属性.
- **FR-012**: `infoAndMove()` MUST 将每个已解析的 `Info` 对象推入
  `pvList` 数组, 保证返回数据完整.
- **FR-013**: `ChessEngine` MUST 支持可选的 `onInfo` 回调参数,
  在引擎输出每行 `info` 时实时调用, 不必等待 `bestmove` 结束.
- **FR-014**: `ChessEngine` MUST 提供 `analyzePosition(fen)` 和
  `stopAnalysis()` 方法, 分别对应 `go infinite` 和 `stop` 命令,
  为后续局面分析功能做好接口准备.
- **FR-015**: info 解析逻辑 MUST 提取为独立的纯函数 `parseInfoLine()`,
  便于单元测试和复用.

### 关键实体

- **EngineConfig**: 单个引擎的配置信息, 包含:
  `id` (唯一标识, UUID), `name` (显示名称), `path` (EXE 文件路径),
  `type` (协议类型: `ucci` | `uci`), `builtin` (是否内置引擎),
  `thread` (线程数), `hashSize` (哈希表大小 MB).
- **EngineConfigFile**: 配置文件整体结构, 包含:
  `version` (配置文件版本号), `engines` (EngineConfig 数组),
  `defaultEngineId` (默认引擎 ID).
- **Info**: 引擎搜索信息, 包含:
  `depth` (搜索深度), `seldepth` (选择性深度), `score` (评分值),
  `scoreType` (评分类型: `cp` | `mate`), `nodes` (搜索节点数),
  `nps` (每秒节点数), `time` (搜索时间 ms), `multipv` (多路 PV 编号),
  `pv` (主变例走法序列).

## 成功标准

### 可衡量的结果

- **SC-001**: 代码库中搜索 `CYCLONE` 或 `cyclone` 返回零结果
  (不含 `.git/` 目录).
- **SC-002**: 用户可在 30 秒内完成自定义引擎的加载
  (从点击菜单到引擎可用于对局).
- **SC-003**: 自定义引擎加载后, 引擎通信(走棋查询)的响应时间
  与内置引擎无显著差异(相同引擎相同局面 ±10%).
- **SC-004**: 配置文件损坏恢复后, 内置引擎功能完全正常,
  无需用户干预.
- **SC-005**: 所有引擎配置操作(加载、移除、持久化)均不阻塞渲染进程,
  符合章程性能标准(原则 IV).
- **SC-006**: 对任意引擎返回的 `info` 行, `parseInfoLine()` 的单元测试
  覆盖率达到 100%, 所有字段解析结果与 UCI/UCCI 协议规范一致.
- **SC-007**: `onInfo` 回调在 `go` 命令执行期间被调用次数 ≥ 1,
  且每次调用的参数为有效的 `Info` 对象.
